# PLAN-1.8 · 暂停/继续、镜像按延迟排序、批量重试

> 目标：1.8.0 在不引入新外部依赖、不改动既有返回契约（只做加法）的前提下，
> 补齐下载管理器最后一块体验缺口（暂停），并把两处「白拿的」改进收进来。

## D1 · 暂停 / 继续

### 语义定义（先于实现）

- **暂停** = 终止当前子进程（SIGTERM → 1s SIGKILL，与取消同一兜底），但终态记
  `paused`（新状态），半包与旁车指纹**原样保留**——与取消的物理动作相同，
  差别只在「用户意图的落点」：取消是「我不要了」，暂停是「我等会儿还要」。
- **继续** = 复用 1.6.0 的 retry 通道（同 taskId、复用请求元数据）。续传安全性
  由既有 `planResume()` 指纹核对兜底，不新增任何路径。

### 设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 暂停信号 | `controller.abort(PAUSE_ABORT_REASON)` | AbortSignal.reason 会随 `AbortSignal.any` 传播，`finishAborted` 据此把终态写成 paused 而非 cancelled——不需要第二个信号通道 |
| 新增状态 | `ProgressState += 'paused'` | 两条轨道都是本插件自有/自有格式占多数；dsh-task-progress 读取端对未知 state 的行为按 running 处理，属可接受的外观退化（轨道二正确显示） |
| 批量中的暂停 | 该条记 `paused`，同批其余条目继续 | 与取消同语义；`BatchItemResult` 加 `paused?: true` |
| retry 白名单 | failed / cancelled / **paused** | paused 行在管理器里复用「重试」按钮（即「继续」），不新增第二个动作按钮——一个位置一个动词 |
| 服务端 op | `op:'pause'`，只对 running 生效 | 与 cancel 同一条纪律：不是错误就如实回 `not-running` / `unknown` |

### 明确不做

- 不做「暂停全部」：与批量取消同构，批量语义下逐条暂停已可用（后续按需加）。
- 不改 aria2 RPC 常驻模式：真·瞬时暂停留给 1.9 的 RPC SPIKE，本轮子进程粒度够用。

## D2 · 自动镜像按探测延迟排序

现状：候选**并行**探测后按候选表顺序取第一个通过校验者。所有候选的探测耗时
已经天然可得（探测本来就有先后），排序是白拿的。

- 每个候选记录探测耗时；**通过校验的候选中取耗时最小者**；耗时并列时按候选表
  顺序（稳定排序）。理由文案带实测延迟（如 `，延迟 412ms`）。
- 「同源证明」三条件不变——排序只影响**谁先被选中**，不影响谁能入选。

## D3 · 管理器「重试全部失败」

- 客户端实现：工具栏加「重试全部失败」按钮，对当前可见列表中
  `failed / cancelled / paused` 的行**顺序**调用既有单行 retry（复用全部行级
  纪律：在途互斥、不传 confirm、成功/失败文案）。
- 不新增服务端批量 op：`startRetry` 的白名单与元数据校验逐条生效，N 次调用
  没有第二种语义；服务端加批量 op 反而要重造一套聚合错误报告。

## 测试计划（正向断言，沿用契约表口径）

1. auto-mirror：两个同源候选，表序靠前的更慢 → 选中更快的；并列 → 保持表序。
2. 暂停端到端：慢速源后台下载 → `pauseRunningTask` → 终态 `paused`（两条轨道）
   → `startRetry` 接受 paused → 续传完成。
3. rpc：`op:'pause'` 对 running / not-running / unknown 三态的回告；
   op 白名单拒绝未知 op（既有用例扩展）。
4. runBatch：批量里一条被暂停 → 该条 `paused: true`、其余条目照常。
5. client：paused 行有重试无暂停/取消；running 行有暂停+取消；点暂停发
   `op:'pause'` 不带 confirm；「重试全部失败」按顺序逐条 retry。

## 回归红线

- 不传新参数时所有命令行与返回结构与 1.7.0 逐字段相同（`paused` 相关字段
  只在真的发生暂停时出现）。
- 取消路径零改动：`abort()` 无 reason 时仍是 cancelled。
