# P1 可行性：多引擎测速与动态并发调整

本文回答 P1「强化智能核心」里最容易被含糊过去的两件事：**「多引擎」到底指什么**，以及
**「动态并发调整」在随包 aria2 上到底做不做得到**。结论全部来自源码行号或本机受控实测。

配套阅读：并发阈值的历史实测见 [README 的「并发阈值是实测的，不是猜的」](../README.md#并发阈值是实测的，不是猜的)。

## 一句话结论

**「动态并发」在 aria2 上「能做到，但不该做」**，而且方向不对称：

- **上调**（下载中把 `-x/-s` 从 1 提到 8）：RPC 返回 `OK`，连接数立刻从 1 变 8，下载**完整成功**（3 次全部 `exit 0`）。
- **下调**（8 降到 1）：RPC 同样返回 `OK`、连接数也立刻掉到 1，但**下载会失败**（`errorCode=1`，落盘缺字节），2 次全部复现。
- 更关键的是**代价与收益不成比例**：上调在 32MB 受控实验里只比固定 8 连接快约 2.5%，
  却要求插件改走 RPC 模式并新增一套生命周期管理（详见 §1.4、§3.4）。

因此本轮建议**不做**下载中动态调并发，改为做两件有实测支撑、成本低得多的事：
**把「本次实际吞吐 + 实际有效连接数」记下来**（§3.2），以及**明确「多引擎」= 多镜像源选择，而不是多后端**（§2）。

受控服务器的设计沿用 README 0.7.0 那节的做法（**每连接限速**，模拟「单连接被限速、多连接能叠加」）。
服务器自身修过两个会污染结论的 bug，如实记下以免后人重踩：
1. `res.on('close')` 在 `res.end()` 之后还会触发一次，必须用 `res.writableEnded` 区分，
   否则二次 `res.end()` 会截断响应；
2. 限速不能按 `res.write()` 返回值分支（那是背压，不是限速），必须固定 50ms 节奏推送。

## 1. 能力边界：下载进行中能不能改 `-x/-s`

### 1.1 命令行方式：不可能

插件当前就是这样起 aria2 的——`buildAria2Args()`（`src/downloader.ts:108-137`）把 `-x/-s/-k`
拼进 argv 后交给 `spawn`（`src/downloader.ts:325`），进程启动后命令行就固定了，没有任何通道能再改它。

### 1.2 RPC 方式：可以，但必须先开 RPC

随包 aria2 支持 JSON-RPC。`--help=#rpc` 列出 `--enable-rpc`（默认 **false**）、
`--rpc-listen-port`（默认 6800）、`--rpc-secret`。**当前插件完全没有用 RPC**
（`src/rpc.ts` 里的 RPC 是本插件给 DSH 进度面板用的 `/api/smartdl.status`，与 aria2 自身 RPC 无关）。

实测（`aria2-rpc-test.mjs`）：`--enable-rpc=true` 启动后，对活动下载调用
`aria2.changeOption(gid, { "max-connection-per-server": N, "split": N })` 返回 `{"result":"OK"}`，
且 `aria2.getOption` 随后读回的 `max-connection-per-server` 确实是新值（`change-up` 场景读回 `8`）。

`aria2.tellActive` 里的 `connections` 字段直接给出**实际有效连接数**，可逐秒观察。

### 1.3 上调与下调不对称（本节的核心实测）

服务器 32MiB、每连接 512KiB/s。第 3.0–3.2 秒发起 `changeOption`，aria2 用默认重试策略（`max-tries=5`）。

| 场景 | `changeOption` 返回 | 连接数变化 | 结果 | 落盘字节 |
| --- | --- | --- | --- | --- |
| 基线：全程 x8，不改 | — | 8 → 8 | ✅ `exit 0` | 33554432 / 33554432 |
| **上调 x1 → x8**（第 1 次） | `OK` | 1 → **8**（t=3.7s） | ✅ `exit 0` | 33554432 / 33554432 |
| **上调 x1 → x8**（第 2 次） | `OK` | 1 → 8 | ✅ `exit 0` | 33554432 / 33554432 |
| 下调 x8 → x4（第 1 次） | `OK` | 8 → 4 | ✅ `exit 0` | 33554432 / 33554432 |
| 下调 x8 → x4（第 2 次） | `OK` | 8 → 4 | ✅ `exit 0` | 33554432 / 33554432 |
| **下调 x8 → x1**（第 1 次） | `OK` | 8 → **1**（t=3.7s） | ❌ `exit 1` | 30618416 / 33554432 |
| **下调 x8 → x1**（第 2 次） | `OK` | 8 → 1 | ❌ `exit 1` | 30592202 / 33554432 |

下调到 1 的失败原因，aria2 自己写在日志里（`--log-level=notice`）：

```
[ERROR] [AbstractCommand.cc:377] CUID#18 - Download aborted. URI=http://127.0.0.1:8813/f.bin
Exception: [DownloadCommand.cc:234] errorCode=1 Got EOF from the server.
[NOTICE] [RequestGroupMan.cc:424] Download GID#72168bb9128d19f7 not complete: …/f.bin
```

`tellStopped` 里的终态是 `errorCode=1`、`errorMessage="No URI available."`。也就是说：
**把 `-x/-s` 降到 1 会让 aria2 丢弃已建立的连接与分片分配，之后它无法重新组织出有效的请求，重试 5 次也救不回来。**

### 1.4 一个必须写下来的对照实验

「下调失败」看起来可能是我的测试服务器接不住 aria2 的重连。为此做了两组对照：

| 对照 | 做了什么 | 结果 |
| --- | --- | --- |
| **no-op 改参** | 调用 `changeOption` 把值设成**与当前完全相同**（x8→x8） | ✅ `exit 0`，33554432 / 33554432（2 次） |
| **只掐连接、不碰 RPC 选项** | 直接 `SIGKILL` aria2 进程 | 服务器能正常支撑后续续传（见下） |
| `changeGlobalOption` 改 `max-connection-per-server` | 全局改 | ✅ `exit 0`，33554432 / 33554432（**该选项对全局无效，下载始终是 8 连接**） |

对照的结论很干净：
- **不是「任何 RPC 调用都会打断下载」**——no-op 改参能完整下完；
- **不是服务器接不住重连**——见 §4.3 的续传实测，同一服务器上 `-c` 续传 4.81s 就补完了剩余字节；
- **是「真的把 `max-connection-per-server` 调小」这件事本身**让 aria2 失败。

> 补充一条容易踩的坑：RPC 调用 `aria2.tellStatus` 时 **gid 传空字符串会被拒绝**
> （`{"error":{"code":1,"message":"Invalid GID "}}`），要么用 `aria2.tellActive`，
> 要么省略 gid 参数。我最初的实验因此拿到空结果，差点误判成「RPC 不可用」。

### 1.5 curl 呢

curl 是**单进程单传输**模型，没有任何运行期接口可以改并发。`--help all` 里的并发相关选项
（`-Z/--parallel`、`--parallel-max`）作用于**多个 URL 并行传输**，不是把单个文件切成多连接；
`--retry` 系列只影响失败重试。插件也没有用这些开关（`buildCurlArgs`，`src/downloader.ts:152-173`）。

结论：**curl 路径上「动态并发」不存在，能改的只有「杀掉重来」**——而杀掉重来会丢掉当前连接，
比不做更慢。

### 1.6 另一个 RPC 模式的硬前置（实测）

`--enable-rpc=true` 时，aria2 **下载完成后不会自己退出**。基线实验里下载在 t≈17s 完成，
进程仍在运行（CPU 0.19s、不退出），必须显式调用 `aria2.shutdown` 才会结束。

这对插件是硬约束：`downloadWithAria2()`（`src/downloader.ts:313-333`）依赖 `runProcess` 的
`child.on('close')`（`src/downloader.ts:287`）来判定完成。**如果直接给现有 spawn 加上
`--enable-rpc`，下载会「成功但永不返回」**，必须先实现 shutdown 生命周期。这条也是 §3.4 成本核算的依据。

## 2. 「多引擎」到底指什么

用户说的「多引擎」有三种可能解释。逐个对照本仓库现状：

| 解释 | 本仓库现状 | 判断 |
| --- | --- | --- |
| (a) 更多下载后端 | 只有 aria2 与 curl 两个（`ARIA2_TARGETS`，`src/downloader.ts:44-49`；`getAria2Path()` 解析不到就回退 curl） | **不是**。加后端（wget / axel / 自研分片器）不会带来「智能选择」，因为插件已经覆盖了「能多线程」与「不能多线程」两种情形 |
| (b) 多个镜像源选择 | **已有雏形**：`mirror: "auto"` 会**并行探测**所有候选镜像，按候选表顺序取第一个通过「长度 + ETag 同源证明」的（`src/auto-mirror.ts:130-146`） | **就是它**。已有的「并行探测」缺的只是「按速度而不是按顺序选」 |
| (c) 多连接聚合 | 就是 aria2 的 `-x/-s`，即当前 `decideConcurrency()` 在做的事（`src/decision.ts:44-47`） | **不是新东西**。这正是 P1 的「动态并发」那半句，与「多引擎」是两件事 |

**依据**：`pickMirrorServingSameFile()` 的注释明确写了「所有候选**并行**探测（串行会让最坏耗时随候选数线性增长），
随后按候选表顺序取第一个通过校验的」（`src/auto-mirror.ts:109-110`）。也就是说插件**已经在同时联系多个源**，
只是选择依据是「表里的顺序」，而不是「谁快」。

因此本文把「多引擎测速」定义为：**对候选镜像源做吞吐测速，按实测速度选源**。
这是 (b)，不是 (a)。理由：这是三者里唯一「已有代码路径、只差一个决策信号」的解释；
而 (a) 是纯增量工作，(c) 就是本文 §1、§3 在讨论的并发本身。

> 注意「竞速」这个词有两种含义，不要混：
> - **探测竞速**（谁先应答 / 谁通过同源证明）——已实现，`Promise.allSettled`（`src/auto-mirror.ts:130`）；
> - **吞吐竞速**（谁传得快）——未实现，本文建议的方案。
> 后者不能靠「并发下同一个文件再取消慢的」实现，那会白烧流量并破坏 §4 的同源前提。

## 3. 「测速」的可行方案对比

### 3.1 方案 A：下载前预探测（先下 N MB 测吞吐再决定并发）

**实测代价核算**（`scale.mjs`，32MiB / 每连接 512KiB/s）：

| 并发 | 实测墙钟 | 实测吞吐 |
| --- | --- | --- |
| x=1 | 85.42s（本次 `exit 1`，见下） | 0.37 MB/s |
| x=2 | 43.72s | 0.73 MB/s |
| x=4 | 27.03s | 1.18 MB/s |
| x=8 | 17.35s | 1.84 MB/s |

> x=1 那次 `exit 1`：85s 的单连接下载在末尾失败。它与本节结论无关（x=2/4/8 均 `exit 0`），
> 但如实记录：**单连接长时间下载在这套受控环境里本身就不稳定**，这也是「保底别低于 2 连接」的一个旁证。

若「先下 2MB 探测、再用同一速率推剩余」，总时间与直接下几乎相等（速率线性时 `probe + rest ≡ total`），
所以**预探测的代价不是时间，而是**：

1. **对 1–8MB 档是净亏**。这一档当前用 x4（`decideConcurrency`，`src/decision.ts:44-47`），
   实测 x4 已是 1.18MB/s；8MB 文件本身只要约 7s，插入一次 2MB 探测等于先把 25% 的字节用单连接重下一遍。
   而 <1MB 走 curl（`SIZE_THRESHOLD`，`src/decision.ts:18`），探测纯属多余。
2. **预探测的速率未必能预测下载速率**。受控服务器是「每连接限速」才有 `≈ 并发数 × 单连接速率` 的线性关系；
   真实服务器常按 IP / 全局限速或根本不限速，单连接探测值外推到 8 连接会系统性高估。
3. **多一次完整请求**，会与 §4 的指纹 / 落盘校验产生新的耦合面。

**结论：不推荐作为主方案。** 它唯一真正有价值的信息（「这个站单连接有多慢」）在真实网络里不可外推。

### 3.2 方案 B：按主机记历史吞吐（本地缓存，下次直接用）

**缓存什么**：不是「猜的并发数」，而是**实测到的观测量**：
`host` → `{ 最近 N 次的吞吐均值, 当时使用的并发数, 当时实际有效连接数, 更新时间 }`。

**为什么这是三者里最划算的**：数据是**下载本身免费产生的**，不需要任何额外请求。
而且插件已经拿到了解析好的速度字段——`parseAria2Summary()` 的正则里
`CN:\d+` 已经被匹配、只是没被取出（`src/progress-parse.ts:23`，返回结构 `ParsedSummary`
只有 `pct/spd/eta`，见 `src/progress-parse.ts:13-20`）。
把 `CN`（实际有效连接数）与 `DL`（速度）一起留下来，就能回答一个当前完全无法回答的问题：
**「我开了 8 连接，aria2 实际用了几条？每条多快？」**

**存放位置**：沿用本仓库既有的「显式可覆盖」惯例——环境变量指定目录，缺省放插件状态目录。
可参照现有的 `DSH_PROGRESS_DIR` / `DSH_DOWNLOAD_PROGRESS_DIR` / `DSH_HOME` 与
`DSH_SMARTDL_MIRRORS`（`src/auto-mirror.ts:44`）的先例。

**失效策略**（必须显式定义，否则缓存会变成另一种「静默失败」）：
- 按主机 + 端口分桶，不按 URL（路径不同但同一站点的带宽是共享的）；
- 只保留最近 N 次（建议 5），用中位数而不是均值，避免一次网络抖动污染；
- 超过 TTL（建议 24h）视为无效；
- **只用于「抬档」，不用于「降档」**：历史慢不足以证明这次慢（可能是临时拥塞），
  而历史快也只是把并发提到当前上限 8，风险有限；
- 缓存读失败 / 格式损坏一律当作「无历史」，回落到现有按大小分档，绝不因此改变下载路径。

**隐私影响**：缓存里会有**主机名**，也就是「这台机器下过哪些域名」。这是新增的本地持久化信息，
必须写进文档与 `docs/SECURITY.md` 的口径里。可选的弱化手段：只存主机名的哈希（sha256 前 16 字节）
——对本用途足够，代价是无法人工排查缓存条目对应哪个站。**建议默认只存哈希**，因为决策只需要「同一个主机再次出现时能对上」。

### 3.3 方案 C：下载中自适应（先小并发、按实测加速）

**在 §1.3 的事实边界下，只有「上调」方向可用。**

| 方向 | 可行性（实测） | 收益（实测） |
| --- | --- | --- |
| 上调 x1 → x8 | ✅ 完整成功，3/3 | 19.5s vs 固定 x8 的 17.35s → **慢 2.2s**；也就是说「先慢后快」在 32MB 上只会更慢 |
| 下调 x8 → x4 | ✅ 成功，2/2 | 30.0s vs 17.35s → 明显更慢（这是刻意的，本就不为提速） |
| 下调 x8 → x1 | ❌ 失败，2/2 | 不可用 |

「先小并发、再按实测加速」的收益上限，取决于「猜错并发」的概率：只有当你**真的猜低了**
（本可 8 连接却开了 1），上调才追回损失。而在 32MB 上，这个「追回」也只值 2.2s——
因为文件太小，慢的那 3 秒占了全程的 17%。
文件越大这个比例越小（1GB 时几乎可忽略），但**实现成本不随文件大小变化**（见 §3.4）。

### 3.4 成本核算：为什么建议「不做」

要用方案 C，插件必须：

1. 给 aria2 加 `--enable-rpc`（当前没有），
2. 因此必须实现 **shutdown 生命周期**（§1.6 实测：RPC 模式下 aria2 不自己退出），
3. 实现一个本地 JSON-RPC 客户端与 gid 管理（注意 gid 空串陷阱，§1.4），
4. 处理「RPC 端口冲突 / 被防火墙拦 / 认证失败」等新失败面，并保证这些失败**不能**让下载挂住，
5. 在 `decide()` 与 `downloadWithAria2()` 之间引入一个运行期控制器，同时不破坏
   `runProcess` 的取消语义（`SIGTERM` → 1s `SIGKILL`，`src/downloader.ts:247-267`）。

这 5 条都是**新增的失败面**，而换来的实测收益是「32MB 上最多 2.2s，且只在猜低时为正」。
按本仓库一贯的「静默失败防护」标准（README「设计上的静默失败防护」一节），
这笔交易不划算。

### 3.5 推荐方案与退化行为

**推荐**：方案 B（按主机记历史吞吐），配合**只上调**的可选优化，且**默认关闭**。

具体到最小可落地的一步：
- 第一步（建议纳入 1.3）：把 `parseAria2Summary()` 已经匹配到、却丢弃的 `CN` 取出来，
  连同 `DL` 一起写进按主机分桶的本地缓存（哈希键、TTL 24h、中位数、只用于抬档）。
  这一步**不需要 RPC**，只改解析器与新增一个缓存模块。
- 第二步（可选，1.4 再评估）：如果缓存数据显示「某主机长期在 x8 下只跑出 x2 的速度」，
  说明瓶颈不在本地并发数，那就**不该调并发**——这本身是有价值的信息，比盲调更有用。

**推荐方案不成立时的退化行为**（必须逐条明确）：

| 失效情形 | 退化行为 |
| --- | --- |
| 缓存文件不存在 / 损坏 / 不可写 | 完全按现有 `decideConcurrency()` 大小分档（`src/decision.ts:44-47`），行为与今天一致 |
| 主机从未见过（无历史） | 同上，不猜测、不加探测请求 |
| 历史数据过期（> 24h） | 同上，并顺手淘汰该条 |
| 缓存目录不可用（只读 / 权限） | 静默跳过缓存，**不得**让下载失败；与 `writeMarker()` 的既有处理方式一致（`src/resume.ts:95-108`，写失败静默忽略） |
| 未来引入 RPC 上调后，RPC 启动失败 | **直接按原并发启动 aria2 的纯命令行模式**，不重试 RPC，不降级为「无并发」 |

最后一条尤其重要：RPC 只是**优化通道**，它挂掉必须退化成今天的行为，而不是变成一个新的失败点。

## 4. 与现有完整性 / 续传机制的相互影响

### 4.1 测速产生的额外请求会不会干扰指纹

**会，如果测速是「另一个 URL 的请求」**。当前指纹的取值链路是：

- `probeUrl()` 用 HEAD，失败 / 405 / 无 `Content-Length` 时退化为 `GET + Range: bytes=0-0`
  （`src/probe.ts:222-266`），并强制 `accept-encoding: identity`（`src/probe.ts:31`，
  理由见 `src/probe.ts:8-16`：不强制会让支持 gzip 的服务器 100% 误报长度）；
- ETag / Last-Modified 从**这次真实会被下载的请求的响应头**里取（Range GET 优先，`src/probe.ts:244-245`）；
- 指纹写进旁车 `.part.json`（`writeMarker()`，`src/resume.ts:95-108`），续传时比对（`planResume()`，`src/resume.ts:190-216`）。

如果「测速」另起一个 URL（例如换镜像前缀）去下 N MB，那份响应的 ETag **不能**当作原始地址的指纹。
**方案 B 不产生额外请求**，因此不触碰这条链路——这是它相对方案 A 的又一处优势。

### 4.2 与落盘校验的相互影响

`verifySize()` 比的是「落盘字节数 vs 探测到的 `contentLength`」（`src/verify.ts:93-118`），
并会在 `content-encoded` 时**跳过**而不是误判（`src/verify.ts:106-110`）。

方案 A 的预探测如果**把探测流量写进了最终文件**，就会直接破坏这条校验；
如果写到临时文件再丢弃，则多出「临时文件清理失败」与「同一 URL 并发请求被服务器限流」两类新问题。
方案 B 与方案 C 都不写额外字节，不影响校验。

### 4.3 与续传的相互影响（含一条关键实测）

实验 `recover.mjs`：x8 启动 → 中途 `changeOption` 降到 1（已知会失败）→ 观察落盘状态 → 再用 `-c` 续传。

```
phase1 changeOption at t=3.0s -> {"result":"OK"} (conn was 8)
phase1 ended t=65.5s status={"completedLength":"24526848","errorCode":"1","errorMessage":"No URI available.","status":"error"}
phase1 file=30618416/33554432 controlFile=true
phase2 resume -c exit=0 wall=4.81s bytes=33554432/33554432 match=true
```

三条结论：

1. 中途降并发失败后，**文件是残的（30.6MB / 32MB）但控制文件 `.aria2` 在**；
2. 因此它**可以**被续传救回来：同一目录再用 `-c` 跑一次，4.81s 补完，`exit 0`，字节数精确匹配；
3. **但当前插件的续传前置会把它丢掉**：`planResume()` 在「远端长度未知 / 本地比远端长 / 指纹不一致」时
   调用 `discard()`（`src/resume.ts:223-236`），而 `discard()` 会**同时删除 `.aria2` 控制文件**。
   这次场景（长度一致、指纹一致）会走「按长度续传」（`src/resume.ts:219`），所以能救；
   但只要指纹因为任何原因不一致，就会连控制文件一起删掉，退化成全量重下。

**这条影响与 P1 无关，但它是本次实验的副产品，值得记下来**：`discard()` 删 `.aria2` 是**有意**的
（`src/resume.ts:229-231` 注释说明：留着它会让 aria2 按旧进度继续）。也就是说
「删控制文件」是为了防止错位续传的正确取舍，不是 bug。本节只是把「因此放弃的恢复能力」写清楚。

### 4.4 与「多镜像源」的相互影响

方案 B 的主机分桶缓存天然支持镜像场景（镜像前缀是独立主机，各自记各自的吞吐）。
但要注意：镜像的**同源证明**（长度 + ETag，`src/auto-mirror.ts:138-139`）与**速度**是两个独立判据，
**速度不能替代同源证明**。任何「谁快用谁」的实现都必须先过同源证明，否则等于把
「下载到什么」交给第三方决定（`src/auto-mirror.ts:9-17` 已把这条边界写死）。

## 5. 明确「不做」的清单

| 不做 | 理由（证据） |
| --- | --- |
| **下载中动态降并发** | 实测 2/2 失败（`errorCode=1`、落盘缺字节），§1.3 |
| **下载中动态调并发作为默认行为** | 需要 RPC 模式 + shutdown 生命周期，且 32MB 上收益 ≤ 0 或 2.2s，§3.3 / §3.4 |
| **下载前预探测吞吐** | 对 1–8MB 档净亏；单连接速率在真实网络不可外推，§3.1 |
| **用「并发下同一个文件、取消慢的」实现多镜像竞速** | 白烧流量、破坏同源证明前提、可能触发服务器限流，§2 / §4.4 |
| **新增下载后端（wget / axel / 自研分片器）** | 「多引擎」的三种解释里最不可能是这个，且不解决任何已知问题，§2 |
| **调高 8 连接上限** | README 已记录：32/64MB 下 x=16 确实更快（23~24 MB/s），但保守维持 8 以避免触发服务器按 IP 限并发。本次实验未推翻该结论 |

## 7. 验收建议（供后续实现阶段使用）

如果采纳方案 B 的第一步，可验收的标准应包含：
